# Передача предметов в игру

KaevCMS может начислять игрокам награды через Donations, промокоды и другие модули. Сначала предметы попадают в **Web Inventory (веб-инвентарь)** CMS, затем игрок выбирает персонажа и отправляет награду на свой игровой сервер.

Для этого используется очередь **`kaev_reward_queue`**. Администратор должен установить её **в базу каждого GameServer, который будет принимать награды**, и подключить обработчик выдачи предметов.

::: warning Важно: установка таблицы — это только первый этап
KaevCMS записывает задания в очередь, **но сама не добавляет предметы в игровой инвентарь**. Для фактической выдачи нужен отдельный обработчик на стороне игрового сервера (плагин, скрипт или сервис). **Универсальный готовый обработчик для всех игровых сборок в поставку CMS не входит.**
:::

## Как работает передача

1. Модуль начисляет предмет игроку в **Web Inventory** на выбранном GameServer.
2. Игрок открывает **Личный кабинет → Веб-инвентарь**, выбирает предметы (до 50 за одну передачу) и персонажа своего аккаунта.
3. CMS проверяет принадлежность персонажа, резервирует выбранные предметы, создаёт UUID операции и добавляет в таблицу `kaev_reward_queue` **отдельную строку на каждый предмет**.
4. Если полный набор строк записан, CMS показывает статус **«Передано» (`queued`)**. Он означает *передачу в очередь*, а **не фактическую выдачу в игре**.
5. Обработчик игрового сервера читает записи со статусом `pending`, безопасно выдаёт предметы персонажу и после успешной выдачи отмечает их как `delivered`. При подтверждённой ошибке использует `failed`.

Поток: **Модуль → Web Inventory → kaev_reward_queue → обработчик GameServer → игровой инвентарь**.

## Шаг 1. Установите таблицу в базу GameServer

Исходный SQL входит в исходники KaevCMS: [`integrations/reward-queue/install.sql`](https://github.com/tkachikaev/KaevCMS/blob/main/integrations/reward-queue/install.sql).

::: danger Выберите правильную базу
SQL выполняется в **игровой базе GameServer**, где хранятся персонажи, **не в базе самой CMS и не в базе LoginServer**. Если у вас несколько независимых баз GameServer, повторите установку для каждой.
:::

**Вариант А — через phpMyAdmin:**

1. Создайте резервную копию игровой базы.
2. В phpMyAdmin выберите **базу нужного GameServer** в списке слева.
3. Откройте вкладку **«Импорт»**, выберите файл `install.sql` из указанной выше папки (или скачайте его из GitHub) и запустите импорт. Можно также вставить SQL из блока ниже во вкладку **SQL**.
4. Убедитесь, что в выбранной базе появилась таблица `kaev_reward_queue`.

**Вариант Б — через SSH (MySQL/MariaDB):**

```bash
# Запускайте из корневой папки KaevCMS, указав реквизиты именно GameServer.
mysql -h GAME_DB_HOST -u GAME_DB_USER -p GAME_DB_NAME < integrations/reward-queue/install.sql
```

**Содержимое установочного SQL** (совпадает с официальным `install.sql`):

```sql
CREATE TABLE IF NOT EXISTS `kaev_reward_queue` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `request_uuid` CHAR(36) NOT NULL,
    `line_number` SMALLINT UNSIGNED NOT NULL,
    `game_server_id` BIGINT UNSIGNED NOT NULL,
    `source` VARCHAR(64) NOT NULL DEFAULT 'web_inventory',
    `cms_user_id` BIGINT UNSIGNED NOT NULL,
    `account_name` VARCHAR(45) NOT NULL,
    `character_id` BIGINT UNSIGNED NOT NULL,
    `character_name` VARCHAR(190) NOT NULL,
    `item_id` BIGINT UNSIGNED NOT NULL,
    `amount` BIGINT UNSIGNED NOT NULL,
    `status` VARCHAR(32) NOT NULL DEFAULT 'pending',
    `attempts` INT UNSIGNED NOT NULL DEFAULT 0,
    `error_message` VARCHAR(500) NULL,
    `created_at` DATETIME NOT NULL,
    `processing_started_at` DATETIME NULL,
    `processed_at` DATETIME NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `kaev_reward_queue_request_line_unique` (`request_uuid`, `line_number`),
    KEY `kaev_reward_queue_status_created_index` (`status`, `created_at`),
    KEY `kaev_reward_queue_character_status_index` (`character_id`, `status`),
    KEY `kaev_reward_queue_account_status_index` (`account_name`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

В файле применяется `CREATE TABLE IF NOT EXISTS` — повторный запуск **не обновляет структуру существующей таблицы**. Если таблица уже существует, но CMS сообщает об ошибке схемы, сначала сохраните данные и сравните колонки с актуальным `install.sql`.

## Шаг 2. Проверьте доступ CMS к очереди

1. Убедитесь, что нужный GameServer добавлен в [настройках игровых серверов](/guide/game-servers) и подключение к его базе работает.
2. Учётная запись БД, используемая **KaevCMS для GameServer**, должна иметь право читать и добавлять строки в `kaev_reward_queue` (`SELECT` и `INSERT`), а также проверять её структуру. Не предоставляйте права на все игровые таблицы без необходимости.
3. В панели CMS откройте **Администрирование → Очередь наград**, выберите конкретный GameServer.
4. Проверьте сообщение: **«Очередь выбранного GameServer доступна и имеет поддерживаемую структуру»**.

Если указано, что таблица отсутствует или её структура неверна, проверьте, что установили SQL именно в базу **выбранного** GameServer. Если очередь недоступна — проверьте подключение и права пользователя БД.

## Шаг 3. Подключите обработчик выдачи предметов

В исходниках есть [контракт очереди и примеры SQL](https://github.com/tkachikaev/KaevCMS/tree/main/integrations/reward-queue):

- `consumer-template.sql` — **незавершённый шаблон**, а не готовая установка обработчика.
- `pending.sql` — чтение ожидающих записей.
- `mark-processing.example.sql` — безопасное взятие записи в обработку.
- `mark-delivered.example.sql` / `mark-failed.example.sql` — фиксация результата после фактической обработки.
- `problematic.sql` — поиск ошибок и зависших задач.

Обработчик разрабатывается или подключается **под конкретную игровую сборку**: он должен проверять персонажа и предмет, правильно выделять игровой `object_id`, соблюдать правила записи инвентаря и предотвращать повторную выдачу при сбоях. Выбирайте поддерживаемый для вашей сборки способ (например, модуль GameServer или отдельный сервис). Не выполняйте прямые INSERT в таблицу `items` по универсальному примеру — структура и механика выдачи отличаются между сборками.

::: warning Защита от дублей
У каждой передачи есть `request_uuid`, у каждого предмета — `line_number`. Их сочетание уникально. Обработчик должен атомарно забирать задания и гарантировать, что повторный запуск **не выдаст тот же предмет дважды**. Отмечайте `delivered` **только после подтверждённой выдачи**, не просто после чтения строки.
:::

## Шаг 4. Проверьте передачу

1. На тестовом сервере выдайте тестовому игроку предмет через поддерживаемый модуль CMS так, чтобы он появился в **Веб-инвентаре**.
2. Войдите под игроком, выберите предмет и своего персонажа, нажмите **«Передать выбранные награды»**.
3. В **Администрирование → Очередь наград** найдите операцию и её UUID. Статус CMS `queued` означает, что запись достигла игровой БД.
4. В базе GameServer проверьте очередь (запрос **только для чтения**):

```sql
SELECT id, request_uuid, line_number, character_name, item_id, amount,
       status, attempts, error_message, created_at
FROM kaev_reward_queue
ORDER BY id DESC
LIMIT 20;
```

5. Убедитесь, что обработчик перевёл строки из `pending` в `delivered` **и предмет реально появился у персонажа**. Без работающего обработчика строки останутся `pending`.

## Статусы и устранение проблем

| Где | Статус | Что означает |
| --- | --- | --- |
| CMS | `queued` («Передано») | Внешняя очередь получила полный состав; выдача **ещё не подтверждена** |
| CMS | `review` («Требует проверки») | Результат записи неизвестен или обнаружен конфликт; не повторяйте выдачу вслепую |
| CMS | `failed` | Запись в очередь не состоялась; резерв предметов возвращён в Web Inventory |
| GameServer | `pending` | Строка ожидает обработчика |
| GameServer | `processing` | Обработчик взял строку в работу |
| GameServer | `delivered` | Обработчик подтвердил выдачу |
| GameServer | `failed` | Обработчик зафиксировал ошибку |

Если статус GameServer долго остаётся `pending` — проверьте работу и логи **вашего обработчика**. Если `processing` завис или есть `failed` — используйте [`problematic.sql`](https://github.com/tkachikaev/KaevCMS/blob/main/integrations/reward-queue/problematic.sql) и журналы обработчика, прежде чем повторять действия.

::: danger Не допускайте двойной выдачи
KaevCMS **не отслеживает конечные статусы игрового обработчика**. Кнопка **«Проверить ещё раз»** в журнале CMS проверяет наличие и состав записей очереди, а **не факт выдачи предмета**. Не удаляйте и не создавайте заново операции из-за `pending` или `failed` на стороне GameServer без расследования: это может привести к повторной выдаче.
:::

Полное описание формата, сценариев ошибок и безопасных SQL-примеров: [интеграция очереди наград в репозитории](https://github.com/tkachikaev/KaevCMS/blob/main/integrations/reward-queue/README.md).
